# 软件开发工作流 Skill

## 概述

这个 skill 用来把“让 AI 帮我写代码”升级成“让 AI 参与完整的软件开发流程”。

核心原则：

- 先澄清需求，再先定测试，再进入设计和实现
- 文档是实现约束，不是事后补充材料
- 一个任务一个上下文，减少 AI 漂移
- 人负责判断与取舍，AI 负责提速与落地
- 测试驱动设计，测试覆盖要先于技术方案落地

## 使用方式

在 Codex 里，不用输命令，直接说目标就行。

例如，不要写：

```text
实现阶段
```

而是写成：

```text
请基于《任务拆解.md》中的 TASK-003 实现当前任务。
请同时参考《需求说明.md》《技术设计.md》《数据模型.md》和《接口契约/认证接口.md》。
只实现当前任务范围，并补齐对应测试。
```

## 适用场景

适合使用：

- 新功能开发，尤其是同时涉及前后端、接口、数据库、权限和测试
- 复杂重构，需要先澄清范围和风险
- 多人协作，需要统一设计和任务边界
- 使用 Codex 时，希望输出更稳定、可解释、可回溯

不建议使用：

- 极小修复
- 一次性原型
- 不值得产出文档的短平快改动

## 快速开始

第一次使用，按下面顺序直接让 Codex 产出文档即可：

1. 建立项目基线
   `请基于当前项目生成《项目基线.md》，内容包括技术栈、架构原则、安全约束、测试策略和禁止模式。`

2. 澄清需求
   `请根据这段需求生成《需求说明.md》，先列出关键假设，再整理用户故事、验收标准、异常场景、范围边界和待确认项。`

3. 先定测试
   `请基于《需求说明.md》生成《测试用例.md》，先覆盖主流程、异常场景、边界条件、权限、安全、性能和回归检查点，确保测试足够全面。`

4. 产出设计
   `请基于《需求说明.md》《测试用例.md》和《项目基线.md》生成《技术设计.md》《数据模型.md》以及《接口契约》目录下的接口文档，确保设计能支撑全部测试。`

5. 拆分任务
   `请基于《技术设计.md》《数据模型.md》《接口契约》和《测试用例.md》生成《任务拆解.md》，按可独立执行的小任务拆分，并补充验证方式。`

6. 按任务实现
   `请根据《任务拆解.md》中的 TASK-xxx 实现当前任务，并优先实现对应测试，再完成代码。`

7. 交付前验证
   `请对照《需求说明.md》《测试用例.md》《技术设计.md》《数据模型.md》和《接口契约》检查当前实现是否一致，并补一份《发布检查清单.md》。`

## 阶段 0：项目基线

目标：生成 `项目基线.md`，定义整个项目都要遵守的规则。

至少应包含：

- 架构原则
- 技术栈与版本约束
- 安全与合规要求
- 目录与命名规范
- 测试策略
- 禁止模式

## 阶段 1：需求澄清

目标：把模糊需求收敛成 `需求说明.md`。

至少应包含：

- 功能概述
- 用户故事
- 验收标准
- 异常与边界场景
- 非功能要求
- 范围边界
- `[待确认]` 问题

## 阶段 2：测试设计

目标：先基于 `需求说明.md` 产出 `测试用例.md`，用测试来约束后续设计。

至少应覆盖：

- 主流程场景
- 异常与边界场景
- 权限与安全场景
- 数据一致性场景
- 性能与回归检查点

## 阶段 3：技术设计

目标：基于 `需求说明.md`、`测试用例.md` 和 `项目基线.md` 生成设计产物。

主要输出：

- `技术设计.md`
- `数据模型.md`
- `接口契约/`
- 可选 `预研记录.md`

设计要求：

- 每条核心测试都能在设计中找到支撑点
- 设计不能绕开已确定的测试约束

## 阶段 4：任务拆解

目标：把设计和测试一起转成 `任务拆解.md`。

要求：

- 单个任务可在一次 Codex 会话中完成
- 测试任务优先于实现任务
- 依赖清晰
- 可并行项标记 `[P]`

## 阶段 5：实现与测试

这个阶段不是输入某个命令，而是**把当前任务与相关文档作为上下文交给 Codex**。

建议输入约束：

- 当前任务描述
- 当前任务对应的验收标准
- 当前任务对应的测试用例
- 相关设计章节
- 相关接口契约
- 相关数据模型
- 项目基线约束

## 阶段 6：验证与交付

目标不是“代码能跑”，而是“实现与文档一致，并且具备交付条件”。

建议检查：

- 核心验收标准是否有验证证据
- 《测试用例.md》中的核心场景是否全部落地
- 接口实现是否与 `接口契约/` 一致
- 数据结构是否与 `数据模型.md` 一致
- 是否存在文档未定义行为
- 是否需要补充 `发布检查清单.md`

## 关键实践

### 先暴露假设

在写 `需求说明.md` 前，先让 Codex 说出它对角色、权限、输入来源、失败行为、兼容性和上线方式的假设。

### 先定测试，再定设计

不要先拍技术方案，再回头补测试。先把《测试用例.md》写全，再让《技术设计.md》去满足这些测试。

### 一次只推进一个任务

不要把多个任务塞给同一个长上下文，否则 Codex 很容易混淆边界。

### 文档和代码一起更新

如果实现和设计不一致，不要只改代码；相关文档也要同步更新。

### 多智能体并行开发

对中大型需求，优先采用多智能体策略：

- 先根据《任务拆解.md》分配独立任务
- 为每个智能体创建单独 Git 分支
- 各分支并行开发、各自验证
- 最后统一做合并、冲突处理和总体验证
