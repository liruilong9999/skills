# 文档驱动多智能体并发开发

## 核心目标

先基于文档建立单一事实源，再拆成可并发执行的工作流，最后统一集成和验收。  
不要先开多个智能体再临时分工；先确认文档、边界、依赖、交付物和验证方式。

## 使用流程

### 1. 锁定文档事实源

优先阅读并排序这些文档：

1. `任务拆解.md`
2. `需求说明.md`
3. `技术设计.md`
4. `数据模型.md`
5. `接口契约/`
6. `项目基线.md`

如果仓库没有完整链路，先补齐文档或明确“当前只能按哪些文档实施”，不要让不同智能体各自猜需求。

### 2. 先确认能否并发

只把满足以下条件的工作拆给不同智能体：

- 输入契约稳定
- 输出边界清晰
- 依赖顺序明确
- 可以独立验证
- 不会同时修改同一批核心文件

优先按这些维度拆分：

- 模块边界
- 接口边界
- 数据模型边界
- 测试边界
- 文档边界

不要按“大家一起改核心循环”这种方式并发。

### 3. 固定主智能体职责

主智能体始终负责：

- 统一读取和解释文档
- 确认分工与依赖
- 给每个子智能体下发精确任务
- 维护共享约束和接口契约
- 合并结果
- 处理冲突
- 执行最终验收

主智能体不要把“需求解释权”下放给子智能体。

### 4. 给每个子智能体最小充分上下文

每个子智能体任务说明必须至少包含：

- 当前任务 ID 或名称
- 目标结果
- 允许修改的范围
- 禁止修改的范围
- 必须遵守的文档
- 依赖的接口、数据模型或测试约束
- 完成后必须返回的内容
- 验证方式

如果任务依赖某一段接口或数据模型，直接把相关文件路径发给子智能体，不要只给抽象概述。

### 5. 先确认分工，再并发执行

在真正启动多个智能体前，主智能体必须先产出一版分工表，至少包含：

| 智能体 | 负责范围 | 输入文档 | 允许修改 | 交付物 | 依赖 | 分支策略 |
|---|---|---|---|---|---|---|
| A | ... | ... | ... | ... | ... | ... |

如果两名智能体都会改同一个核心文件，默认不并发，除非一人只读审查、一人实现。

### 6. 分支策略

默认不要一上来就给所有子智能体创建独立分支。先按任务风险决定：

- 实现型子智能体，且会修改代码、配置、接口、数据模型或测试：默认独立分支
- 多个实现型子智能体并发推进不同模块：默认独立分支
- 审查型子智能体：默认不创建分支
- 只读分析型子智能体：默认不创建分支
- 只补文档、且不会与实现并发冲突时：可不创建分支
- 只补测试、且明确不会和实现修改同一文件时：可不创建分支

满足以下任一条件时，必须独立分支：

- 会修改核心实现文件
- 会修改接口契约或数据模型
- 会运行后续需要提交的真实代码变更
- 可能与其他子智能体修改范围重叠

满足以下全部条件时，可以不创建分支：

- 任务是只读审查或信息收集
- 不写仓库跟踪文件
- 不参与最终代码合并

主智能体在下发任务时必须明确写出：

- 是否创建分支
- 分支由谁创建
- 子智能体是否只允许在该分支内工作

如果使用分支并发，优先采用“一名实现型子智能体一个分支”的规则，不让多个实现型子智能体共享同一分支。

### 7. 并发后的集成顺序

集成时按这个顺序执行：

1. 合并契约与数据模型相关结果
2. 合并核心实现
3. 合并接口层与调用层
4. 合并测试
5. 回写文档
6. 做最终联调与回归

不要先合并表现层，再回头补底层契约。

## 子智能体任务模板

按需使用 [references/subagent-prompts.md](references/subagent-prompts.md) 中的模板，至少覆盖：

- 实现型子智能体
- 测试型子智能体
- 审查型子智能体
- 文档同步型子智能体

## 分工规则

- 一项任务只能有一个最终负责人。
- 同一接口契约只能有一个智能体拥有修改权。
- 同一数据模型只能有一个智能体拥有修改权。
- 同一实现分支只能对应一个实现型子智能体。
- 主智能体负责跨任务依赖，不让子智能体相互协商边界。
- 子智能体完成后，先回主智能体，再决定是否继续派生新任务。

## 何时不要使用多智能体

遇到以下情况先不要并发：

- 需求本身还在变化
- 文档彼此冲突
- 任务规模很小
- 核心改动集中在单个复杂文件
- 关键接口还未定稿

## 完成定义

这类并发开发任务只有同时满足以下条件才算完成：

- 分工表和实际修改一致
- 子智能体产出都能映射回原始文档
- 没有越权修改契约
- 测试和验收点已执行或明确记录未执行原因
- 文档、代码、测试三者一致
